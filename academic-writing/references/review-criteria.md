# 逐项执行写作规则

本说明解释既有规范的核对方法，不新增正文写作要求。规则原文仍以 `SKILL.md` 及其7份规范为准；[完整规则表](review-criteria.json)保留原文定位、适用条件、检查动作、所需证据和失败判据。

## 先建立受审范围

先写清用户要求、读者背景、实际受审正文版本、阅读范围以及未核查的材料，再生成规则台账。108个条目是检查分组，不是108句独立规则：同组包含的原文子要求也要分别核对。每个台账保留所有编号，不能省略尚未执行的规则。

通用表覆盖8份规范的374个正文块。例句、填写模板、导航和补充链接保留排除理由；不能把示例中的标题、结构或实验做法变成所有任务的要求。项目或用户的额外要求另建扩展表，不覆盖通用表。语言和任务条件以当前中文任务为准。

## 使用检查工具

以下路径以技能目录为当前目录。`--root` 是对应规则全文的根目录；历史复核须恢复相应历史规则和台账，不能拿现行表验证旧结论。

```sh
python3 scripts/check_review_records.py catalog --root . --catalog references/review-criteria.json
python3 scripts/check_review_records.py init --catalog references/review-criteria.json --output review-r1.json
python3 scripts/check_review_records.py record --root . --catalog references/review-criteria.json --record review-r1.json
python3 -m unittest discover -s scripts -p 'test_check_review_records.py'
```

`init` 只生成待检查记录，不预设通过、不适用或范围外，也拒绝覆盖已有记录。可用下列方式逐项查看完整动作与原文子要求，避免一次加载整张表：

```sh
python3 -c 'import json; d=json.load(open("references/review-criteria.json")); print(json.dumps(next(c for c in d["criteria"] if c["id"]=="FP01"),ensure_ascii=False,indent=2))'
```

## 怎样填写一次实际检查

记录对象保留日期、记录者及其角色、规则表 SHA-256。`scope.targets` 与 `artifacts` 中的路径、正文版本、文件 SHA-256 和阅读范围一致。正文与记录本身均保留完整可恢复位置：已提交版本用 Git 的仓库、提交及相对路径；未提交草案用独立完整快照，不能仅填写当前可变文件自身。

每项填写实际执行动作 `performed_action`、实际检查单元 `units`、具体判断 `reason`、定位证据 `evidence` 和关联问题 `findings`。证据包括文件对象、短引、定位及解释；短引必须确实出现在登记版本中。多个规则可以引用同一段，但要分别说明该段为何支持各自判断。规则原文不是正文通过的证据。

| 状态 | 何时使用 | 必须留下什么 |
|---|---|---|
| `pass` 通过 | 已核对范围内所有适用单元及全部子要求 | 全部适用单元 `applicable_units` 与实际检查单元相符；每个子项有动作、证据及判断 |
| `fail` 未通过 | 已找到明确违反规则的文字 | 原文位置、理解或技术缺口、问题编号与实际检查动作；其余未读子项仍待检查 |
| `pending` 待检查 | 尚未读完、只核对部分单元，或缺来源/前置知识 | `missing` 指出缺什么；部分已查内容也保留动作和证据 |
| `not_applicable` 不适用 | 实际材料没有触发该规则的条件 | 已查看的上下文与条件不成立的具体理由；不能因为材料缺失就判不适用 |
| `out_of_scope` 约定范围外 | 条件可能成立，但用户约定本轮不查 | `scope_basis` 写明约定依据及边界；与尚未完成的范围内工作分开 |

组合条目中的 `subchecks` 对照表内 `requirements`。子项保留原句便于回查；涉及示例时只执行该句的通用约束，具体对象和组织选择仍限于示例条件，不能要求所有章节都照做。子项也使用上述五种状态。不能只查一个例子就把整组标为通过；有一项待核或未通过，整组不能通过。原文条款可能重复映射到多个分组，这不是多个独立新增要求。

## 一个局部检查的记录示例

下列紧凑示例展示字段如何连接；它不是正文修订或全部规则验收。JSON用`init`生成其余待检查项，只填写实际检查到的部分。

| 字段 | 示例填写 |
|---|---|
| 规则与对象 | LG03，当前版本第30行的第4、5句；源文件版本与摘要在台账元数据中登记 |
| 实际动作 | 比较“相对于原环境的下降”和“几乎没有下降”，检查下降的究竟是风险、准确率还是其他表现 |
| 证据短引 | “绝对风险和下降幅度需要一起看” |
| 判断 | 前句讨论风险，风险变差通常增加；“下降”没有说明指标，读者无法唯一确定比较方向 |
| 状态与问题 | fail，关联F01；正文未修改，未关闭问题 |
| 组合子项 | 对象与关系要求未通过；尚未读到的前文或其他子要求保持pending，具体示例条件未触发时才记不适用 |
| 其他规则 | 没有执行的规则保持pending；量词作用域局部通过不能证明整句易懂 |

完整记录仍保留可恢复正文、受审记录和定位证据。普通短句润色可用原规范的紧凑方式；本工具用于用户要求逐项留存的任务，不强加给所有小修改。

## 怎样关闭问题和复核记录

问题状态分别为待修改、已改待复读、复读未通过、复读通过、有据撤销。关闭项绑定两个不同的实际正文版本、改前和改后原句，并留下对改后上下文的复读证据及复读者、版本、范围。建议、聊天改写和修改承诺不能代替改后正文。撤销误报绑定原正文、反证及对原版本的上下文核验。

独立复核者阅读锁定的完整输入，核查规则覆盖、适用条件、实际动作和证据判断；复核范围按实际读取量说明。规则表本身也须核对：是否漏规则、把选项强化为强制、把示例泛化、缩窄适用范围、或把多个子要求合并后遗漏。

记录结论与正文结论分别填写。工具核对来源与版本、漏项、证据短引、状态约束及关闭条件，不能判断读者是否真的理解、解释是否充分、原文映射是否语义正确、单元清单是否真的覆盖全文，也不能证明复核者独立。结构检查通过后仍需阅读复核。正文有待修改或待核项时，不得以记录合格替代正文验收。
